## Rationale (short)

- Hit count on pending/respond/create/GET is **expected**. The lot is about SQL-per-request and duplicated token I/O, not volume.
- No P1: error rates are ~1/119k; JDBC waiters absent; heap idle ~200 MiB.
- `KeyRotationService.checkAndPromotePendingKeys` (~19.7k hits, mean 3.04 ms) stayed **out of the lot** — scheduler cost, not the churn protocol path. Revisit if a later pass shows it on the request thread.

### 1 — JM-001 (defer)

8 SQL at ~7.9 ms wall is an acceptable create baseline for this workload. Do not open a campaign on hit count or on collapsing access-control / audit / insert in the same pass.

Parked if a later pass shows the Admin filter as the real bottleneck (do **not** drop sliding TTL; idle-extend stays):

- **A1 (first cut):** reuse the `AdminToken` already loaded by `validateTokenWithRelations` in `AdminTokenAuthenticationFilter` instead of `updateTokenLastUsed` doing a second `findByBearerTokenHashAndActiveTrue`. Drops SQL #2 only. POST 8→7, GET 4→3. Product unchanged (still one `UPDATE` per request).
- **A2 (optional after A1 + re-measure):** throttle the `UPDATE` (e.g. only if `last_used_at` is older than 30–60 s). Under churn-style bursts most writes vanish; sliding TTL still holds if the threshold is much smaller than `expirationHours`. Trade-off: coarser `last_used_at`. Revocation via `active = false` is unrelated and stays immediate.

Locus: `AdminTokenAuthenticationFilter.tryAuthenticateWithPlainToken` → `AdminTokenValidationService.updateTokenLastUsed`. Same mechanism as JM-002.

### 2 — JM-002 (defer)

Spring view of the same extra find+save. Not a second campaign. A1/A2 stay on JM-001.

### 3 — JM-003 (skip)

Required Admin auth `SELECT` (JOIN FETCH admin/tenant/integration) plus recovery/expiry/tenant/enrollment guards. Caching would delay `active = false` without an invalidation path. Expected cost of hash-only DB sessions.

### 4 — JM-004 (skip)

`@PreAuthorize canAccessAuthAttempt` on GET is the object split. Global Admin is a no-DB short-circuit; Tenant Admin (churn) walks attempt → enrollment → tenant. `getById` then reloads the attempt — accidental extra SELECT, same family as A1, not worth a campaign at 1.38 ms. Do not drop the check.

### 5 — JM-005 (skip)

`canAccessEnrollment` on POST create is the Tenant Admin object check (Global Admin short-circuits). Create then reloads enrollment — same extra-SELECT family as JM-004, 1.03 ms. Isolation first.

### 6 — JM-006 (skip)

Pending ~8 SQL / 9.23 ms (respond sibling ~9 SQL / 9.1 ms) is the protocol path: claim `FOR NO KEY UPDATE` (0.32 ms — not lock wait), enrollment, device-proof uniqueness, attempt update, audit + `nextval`, tenant/integration for audit. Wall time is more CPU (signature verify) than JDBC. Changing this is a program, not hygiene. Revisit only if pending mean diverges from respond or the lock mean jumps.
