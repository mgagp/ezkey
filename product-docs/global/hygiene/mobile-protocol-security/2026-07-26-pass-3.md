## Rationale (short)

Filled after the HITL turn — do not pre-authorize remediation in this open note.

### 1 - MOB-017

**Operator framing (2026-07-26):** the operator's original mental model was that the mobile app had
moved from "too many keys in StrongBox" (one RSA key per enrollment) to "one single StrongBox key
for the whole app that derives the other keys," and asked whether an intermediate model — one
private key per **installation** trust zone, in `SecureStore`/`StrongBox` — would be a better
middle path, given the product's multi-installation posture (one phone, several independent Ezkey
sites).

**Corrected current-state finding (agent re-read, 2026-07-26):**

- **Device signing keys are not the single-key artifact.** Each enrollment still gets its own,
  independently generated EC P-256 keypair in `Android Keystore`/`StrongBox`
  (`getEnrollmentAlias(enrollmentId)` in `EzkeyCryptoModule.kt`), with the alias already
  installation-scoped since MOB-011 (`deriveLocalEnrollmentId`). `ADR-MOB-0002` explicitly rejected
  "a single global key for all enrollments" in 2025-07-20 — that was never implemented, and there is
  **no derivation chain** (no HKDF/ECDH master key) anywhere in the current tree. This axis is
  already at least as isolated as the operator's proposed middle path and is **out of scope** for
  this finding.
- **The one real "single key" artifact is the app-level AES seal key** (`ezkey_app_seal_v1`,
  `ADR-MOB-0004`, 2026-05-03), whose only job is encrypting `enrollmentProofToken` and
  `integrationPublicKey` at rest in AsyncStorage — not device identity material. `ADR-MOB-0004`'s
  rejected alternatives covered "one key per enrollment" (slot pressure) but never evaluated "one
  key per installation."
- **Existing AAD scoping already provides enrollment-grain fail-closed authentication** even with a
  shared seal key: `logicalKey` values built in `enrollmentStorage.ts`
  (`ENROLLMENT_PROOF_TOKEN_KEY_PREFIX + '.' + id`, `INTEGRATION_PUBLIC_KEY_KEY_PREFIX + '.' + id`)
  are passed as AEAD AAD in `SealedSecretEnvelope`, and `id` is already the installation-scoped
  local enrollment handle. A coding bug that supplies the wrong logical key already fails closed
  today (GCM authentication failure) — at a finer grain (per enrollment) than "per installation."

**Narrowed finding:** should the single app-level AES seal key become one key per installation
trust zone (`ezkey_seal_{installationId}`) instead of one key for the whole app? This is local
storage hardening only (per `ADR-MOB-0004`'s own boundary statement) — it does not touch signing-key
generation and requires no Auth API / OpenAPI change.

**Assessed value (honest, not overclaimed):**

- Self-hosted single-installation operators: no change (1 installation = 1 key today either way).
- Multi-installation users (realistic order of magnitude: 1-3 installations per phone): a bounded,
  real defense-in-depth improvement if an in-process bug or compromised dependency invokes
  `sealSecret`/`unsealSecret` across installation boundaries — but a **modest** one, since an
  attacker who already controls the JS bridge call site can still supply the correct
  `installationId` for the specific installation it wants. This is not a strong new adversarial
  isolation guarantee and must be worded accordingly (same guardrails as `MOBILE_CRYPTO_REFERENCE.md`
  — no "cryptographic installation isolation" or passkey-equivalence claims).
- Does not recreate the "StrongBox slot pressure" objection that killed the per-enrollment seal-key
  alternative in `ADR-MOB-0004`, because installation count is expected to stay small (1-3 typical).

**Decision (2026-07-26 Grill Me):** **fix** (program).

- Cutover posture: **greenfield** — no migration path from the shared `ezkey_app_seal_v1` key; treat
  as a breaking local-storage change, same posture as MOB-011 (no production fleet yet).
- Scope confirmed bounded: `enrollmentStorage.ts` choke points (`saveEnrollment`, `replaceAll`,
  `deleteEnrollment`, `clearAll`) already carry the full `StoredEnrollment` (nested `installation`)
  at every call site, so threading `installationId` through is not expected to be more invasive than
  estimated.
- Wording guardrail carried into implementation: describe the change as local at-rest defense-in-depth,
  not as a new cryptographic installation-isolation guarantee (an in-process attacker that already
  controls the native bridge call site can still target one installation's key).
