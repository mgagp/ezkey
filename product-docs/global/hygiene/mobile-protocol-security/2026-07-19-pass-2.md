### 1 - MOB-011

HITL briefing completed 2026-07-19: wizard sets local crypto/storage identity from server `enrollmentId` only; `installation` is UI/routing metadata and does not scope Keystore aliases or sealed-secret keys. Collision scenario accepted as clear.

**Observation scenario (consolidated from closed analysis handoff):**

1. User enrolls on installation A; server A allocates `enrollment_id = 1` → local id `"1"`, Keystore `ezkey_enrollment_1`, seals under `…proof-token.1`.
2. Same phone enrolls on installation B; server B independently allocates `enrollment_id = 1`.
3. Wizard B reuses id `"1"` → Keystore `containsAlias` reuses A’s EC key; `saveEnrollment` drops A’s metadata row and overwrites seals for id `1`.
4. UI still presents two installations; crypto/storage isolation is gone.

**Non-claim:** local multi-installation isolation failure — not a remote MFA bypass of a single honest Auth API over TLS.

**Decision (2026-07-20 Grill Me):** **defer (program)** — not a hygiene-sized fix.

- Multi-install is an end-to-end product claim (crypto included); enrollment-id-only local identity was unintentional framing debt.
- Installation = normalized Auth URL (no installation UUID); enrollment **belongs to** installation trust zone.
- Two sequential activities: (1) trust-zone canon → (2) full local identity + Keystore/seal handles + MOB-013 + MOB-016 as one design (“first principles”, outside production).
- Draft identity scoped at bind (**7A**); Keystore still created in finalize before verify; orphan cleanup in same chantier.
- Preferred local shape **O3** (deterministic safe handles from installationId + serverEnrollmentId); O4 opaque UUID acceptable with same uniqueness invariant.
- Auth API numeric `enrollmentId` unchanged; no special per-install StrongBox partitioning beyond collision-free handles.

**Canon:** [`I-2026-07-20-mobile-installation-trust-zone-canon`](../../backlog/ideas/I-2026-07-20-mobile-installation-trust-zone-canon.md) / [`TB-2026-07-20-mobile-installation-trust-zone-canon`](../../backlog/TB-2026-07-20-mobile-installation-trust-zone-canon.md) — **done** 2026-07-20

**Identity + crypto:** [`I-2026-07-20-mobile-installation-scoped-enrollment-identity`](../../backlog/ideas/I-2026-07-20-mobile-installation-scoped-enrollment-identity.md) / [`TB-2026-07-20-mobile-installation-scoped-enrollment-identity`](../../backlog/TB-2026-07-20-mobile-installation-scoped-enrollment-identity.md) — **done** 2026-07-23 (PR [#401](https://github.com/mgagp/ezkey/pull/401); unit + Pixel multi-install smoke)

### 2 - MOB-012

HITL briefing completed 2026-07-19: `setUnlockedDeviceRequired(true)` from API 30 on enrollment EC and app seal keys with `setUserAuthenticationRequired(false)`, against Android’s Android 12–14 / “use only on 15+” warning (incl. auto-delete on lock-screen removal).

**Decision (2026-07-23 mini Grill Me):** **fix**.

- Gate: API **35+** only (`VANILLA_ICE_CREAM`) via `shouldRequireUnlockedDevice()`.
- Apply to **both** enrollment EC and app seal generators.
- **Forward-only** for already-minted keys (no production fleet; DEV clear-all / re-enroll acceptable).
- Out of scope: CryptoObject / `setUserAuthenticationRequired(true)` (MOB-001 Track B); seal-loss UX (MOB-015); `minSdk` bumps.

**Closeout 2026-07-23:** implemented in `EzkeyCryptoModule.kt`; instrumentation asserts `KeyInfo.isUnlockedDeviceRequired` matches the gate. Ephemeral handoff deleted.

### 5 - MOB-015

HITL briefing completed 2026-07-19: `listEnrollments` broad catch → `[]`; missing sealed proof/integration key silently drops rows — crypto/storage failure looks like healthy empty.

**Decision:** **fix**.

**Grill Me + UI contract (2026-07-25):** product posture zoom-out — do not expose internal failure taxonomy to the end user. One human-facing state for all storage/crypto vices: *unusable on this device; remove and re-enroll via admin*. Fine reasons stay in logs / `__DEV__` / tests.

| Situation | Surface | Intent | Actions |
| --- | --- | --- | --- |
| Mixed healthy + broken | Home inline row | Unusable here; ask admin to re-enroll | Remove on row; Detail; existing `+` |
| All broken / collection unreadable | Home | Not Welcome empty | Clear all / remove / re-enroll |
| Broken selected | Detail | Same human copy | Remove; no auth actions |
| Danger Zone `clearAll` | Settings | True local reset | Wipe enrollments **and** `ezkey_app_seal_v1` |

Fail-open list visibility; fail-closed auth. Tone: unreadable/unusable — not breach language. No new support flow.

**Closeout 2026-07-25:** **Fixed**. `listEnrollmentsDetailed` (healthy / broken / collectionError);
mutations preserve broken rows (raw-metadata writes); Home inline unusable row + unusable-local
notice; Detail unusable state (no auth actions); Danger Zone lists broken rows; `clearAll` sweeps
orphaned secrets and deletes `ezkey_app_seal_v1` (new native `deleteAppSealKey`); EN/FR copy; unit
tests (storage failure modes + seal wipe). Pixel functional relecture OK (operator). Ephemeral
handoff deleted after design reinjection gate.
