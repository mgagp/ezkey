## D1 — Re-encryption batch UI: sync vs async button behavior

> Verbatim (FR):
>
> Dans la batch de réencryption de la BD, on a différents boutons : deux boutons pour activer la batch, soit que l'on clique sur la réencryption immédiate ou que l'on demande de créer la batch de réencryption sans exécuter ces deux actions séparées. J'ai remarqué qu'il me semble y avoir une différence de comportement. Lorsqu'on demande pour une clé spécifique sa réencryption, dans le UI admin, l'action semble se faire de façon synchrone et donc le bouton reste là pendant tout le temps que la batch s'exécute pour vrai. C'est ce que je crois, c'est une perception à valider. Si ce n'est pas le cas, il faut trouver pourquoi ça semble bloqué un certain temps. Si c'est bien le cas, et bien ce n'est pas le bon comportement, parce que le jour où il y aura des centaines de milliers de records à réencrypter, on ne peut pas les faire live pendant que l'appel HTTP à l'API reste bloqué. Et pour ce cas, il faut s'assurer que, dans le fond, qu'on crée la batch et qu'on l'exécute immédiatement et que le bouton ne fait que déclencher ces deux actions de sorte qu'on ne bloque pas. On revient dans le UI et on peut visualiser dans le tableau existant l'état d'évolution des batchs de réencryption.

## D3 — API key acceptance on Admin API: configurable / deployment profile

> Verbatim (FR):
>
> Pour l'utilisation des API qui permettent de créer une demande d'authentification, présentement ces API sont disponibles sur le Admin API, ainsi que sur le Integration API. L'une des différences, c'est que, lorsqu'on fonctionne avec une clé d'API, on valorise d'utiliser le Integration API, qui est plus léger et qui fonctionne avec Virtual Thread, qui est fait pour encaisser du load. Donc, la petite amélioration ici, c'est que je crois que, présentement, on accepte les clés d'API autant sur Admin API que sur Integration API. Cependant, j'ai réalisé, il y a quelque temps, que j'avais une erreur de configuration. Je croyais que j'avais un setup clean start avec mes apps qui utilisaient le Integration API, alors qu'en fait, incluant avec la clé d'API, le SDK Java pointait vers l'Admin API. C'est fonctionnel, mais ça peut être trompeur.
>
> Ce que je veux faire, c'est qu'on ait un flag dans l'Admin API qui permet d'activer ou pas le fait d'accepter une clé d'API sur l'Admin API. Au fond, c'est de se doter d'une façon de forcer, par paramétrage, qu'une clé d'API ne soit usable qu'avec le Integration API. En ce qui concerne la valeur par défaut à adopter, on peut en discuter, mais je crois que je penche pour une approche sécurité par défaut. Et dans la vraie vie, étant donné qu'Integration API est positionnée comme étant le moyen d'intégration par clé d'API, ça suggère fortement que, par défaut, on devrait refuser de fonctionner avec des demandes d'authentification avec les API sur Admin API. En fait, il faut peut-être se poser la question un peu plus loin et savoir et vérifier si on devrait carrément cesser d'accepter les clés d'API sur Admin API.
>
> Le petit bémol que j'ai, c'est que dans le positionnement de produits d'Ezkey, on valorise la simplicité et une approche self-hosted. Je peux quand même voir une certaine valeur à accepter qu'une clé d'API soit utilisable sur le Admin API. C'est-à-dire que, par exemple, pour faire un parallèle, dans le mode multitenant, on n'est pas obligé d'utiliser le multitenant. Quelqu'un qui décide d'adopter la plateforme pourrait décider de créer un global admin et, en tant que global admin, gérer ses intégrations et ses enrôlements sans passer par un découpage qui impliquerait la création d'un tenant.
>
> Et ça peut être un modèle acceptable ou supporté. C'est pour le cas où on a une PME, il y a seulement une personne, une intégration. On ne veut pas forcer la cérémonie de création, de séparation des rôles, avec un global admin et un tenant admin. Donc on accepte que le global admin peut avoir un mode simplifié qui gère tout. L'analogie ici, c'est que dans le cas de la séparation des binaires au niveau des API pour l'API key, à mon avis, c'est quand même le même principe qui s'applique. Quelqu'un, dans le même ordre d'idées, pourrait décider d'approcher l'installation de la plateforme avec le minimum et déployer uniquement le Admin API et le Authentication API. L'Authentication API, je crois que ça ne se négocie pas. Il faut que ce soit séparé. Ça reste séparé, c'est logique. Par contre, le Admin API versus l'Integration API, c'est là que je vois un parallèle avec l'analogie du global admin et tenant admin dans une approche simplifiée. On ne veut peut-être pas forcer, à tout prix, notre installateur de plateforme Ezkey à avoir un binaire séparé pour les intégrations s'il veut le profil d'installation de base.
>
> Ce serait à discuter pour confirmation, mais honnêtement, c'est la bonne posture de produit qui respecte les valeurs du produit de pragmatisme et de simplicité. Au niveau des validations, c'est la même force de validation. L'idée d'Integration API, c'est pour scaler et aussi avoir une surface d'attaque réduite en limitant les API aux clés d'API et seulement ce qu'il faut pour créer, attendre et canceller une demande d'authentification. Dans tout ça, ça semble quand même un compromis acceptable.

## D4 — Checkpoints: handling of detected audit-sequence integrity breaks

> Verbatim (FR):
>
> Dans le Admin API, au niveau des checkpoints logs, j'ai observé qu'on a un problème pour normaliser une situation exceptionnelle. Ce qu'on a déjà prévu à ce niveau-là, c'est que si on a une panne complète, on va avoir un gap d'une certaine durée. Là, il faut faire un gap declaration pour expliquer, avec une justification, que de telle heure à telle heure, par exemple, il n'y a pas d'activité, mais que c'est normal. On ajoute une entrée dans la BD pour identifier et justifier une période creuse.
>
> Dans le même ordre d'idée, si on a une dégradation partielle, par exemple, le Admin API tombe et on sait qu'il joue le rôle de heartbeat avec les checkpoints à toutes les 5 minutes. Après une période de grâce de la deuxième tranche de 5 minutes moins une zone tampon, typiquement 1 minute, on entre dans la zone où l'Integration API et l'Authentication API vont constater qu'il n'y a plus de chaînage cryptographique de checkpoint qui sert aussi de heartbeat et vont tomber en mode dégradé et refuser d'entamer de nouvelles activités d'authentification. Ils vont compléter ce qu'il y a en cours pour refuser des nouvelles actions, tant que le heartbeat n'est pas restauré, c'est-à-dire que le Admin API a repris du service et que la déclaration d'alerte correspondante a été faite. D'ailleurs, l'Integration API et l'Authentication API génèrent une alerte dans une table des équipements avec l'API pour indiquer qu'ils entrent dans l'état dégradé. Bref, toute cette mécanique est en place là où on a une limitation pour les checkpoints.
>
> C'est si je manipule volontairement la ligne temporelle des audits, par exemple, tout simplement en supprimant un audit quelque part. À ce moment-là, lorsque je demande une validation d'intégrité temporelle de séquence d'audit, c'est détecté, et ça, jusque-là, ça va bien. Le problème, c'est que on n'a pas de mécanisme, lorsqu'on le détecte, pour générer une alerte et faire une prise en charge similaire au mécanisme qu'on a présentement.
>
> Donc là, il faut déterminer :
> - comment on va faire cette prise en charge
> - comment on va le déclarer
> - comment on va le rectifier
> - comment on va, dans le fond, intervenir sur la table des checkpoints et des incidents opérationnels associés pour faire une déclaration qui va faire en sorte qu'après ça on voit que cette séquence brisée cryptographiquement est expliquée et réattachée
>
> Donc là, il y a un petit peu de prise en charge conceptuelle de cette notion-là qui va être à clarifier.

## D5 — Integrity validation strategy: windows, nightly batches, effort modulation

> Verbatim (FR):
>
> L'item ici, c'est un peu en lien avec l'item précédent sur les checkpoints et les incidents. La différence ici, c'est que l'on fait le point et un peu de reverse engineering sur la notion des checkpoints et des validations d'intégrité qu'on fait. C'est-à-dire que, là, par exemple, pour le chiffrage cryptographique des checkpoints, on a une fenêtre roulante d'une heure. C'est-à-dire qu'à chaque fois que la batch roule, on attache les 5 dernières minutes ensemble et on crée le checkpoint et on fait une validation sur une fenêtre en arrière de 1 h.
>
> L'extension de ça, c'est que si on détecte un problème, on génère un événement et on le prend en charge. Sauf que là, ce n'est pas assez clair. Qu'est-ce qui se passe si la fenêtre d'une heure a des trous multiples? Là, je ne me souviens pas, ce n'est pas bien spécifié. Donc quelles sont les situations plus limites qu'on devrait prendre en charge et comment ça va être pris en charge en termes d'alerte? Comme, par exemple, si il y a une manipulation dans les audits et que, après 3 jours, par exemple, il y a un audit supprimé, comment on le détecte? C'est là qu'on a une zone d'ombre.
>
> Il faut voir quelles sortes de mécanismes on veut pour valider l'intégrité. Pas systématiquement, parce que ça a des coûts, mais en même temps, si on ne vérifie jamais rien, quelqu'un pourrait manipuler l'historique. Donc il ne faut pas générer de la complexité et rendre le système non performant et complexe pour faire des validations dans le passé systématiquement. Je comprends que ça, ce n'est pas de bon sens, mais en même temps, il y a peut-être une zone où on veut faire des validations additionnelles ou un peu systématiques ou des batchs de nuit qui vont vérifier des blocs prédéterminés, par exemple, à l'image de ce qu'on fait pour les checkpoints sur la période roulante d'une heure, qu'on vérifie que tout est attaché.
>
> L'idée de ça, c'était que s'il y a un ralentissement, s'il y a un mini downtime, on s'attend qu'il va y avoir des alertes ailleurs, par exemple PRTG, je sais pas moi qui va vérifier ou un Grafana qui vérifie que la machine est down. Et puis là, il y a un opérateur qui, dans une heure, supposons, va avoir le temps de venir vérifier ce qui se passe, repartir la plateforme Ezkey pour s'assurer que tout est up. Donc la période de grâce d'une heure, c'est pour que les petites interruptions momentanées soient rattrapées facilement, sans effort, parce que la batch est proactive à vérifier chaque tranche de 5 min dans la fenêtre d'une heure. Donc, déjà, là, est-ce qu'une heure est suffisante? Est-ce qu'on devrait être entre deux jeux et dire : « C'est pas une heure, c'est 4 h »? Peut-être, ça serait à considérer.
>
> Et puis cette analogie, c'est aussi pour le fait que les validations d'intégrité cryptographique de checkpoints et de séquences, là, est-ce que par exemple on devrait avoir une batch qui roule la nuit et qui va vérifier les 24 dernières heures? Et le lendemain matin, s'il y a un problème, produire une alerte ou quelque chose comme cela?
>
> Est-ce qu'on devrait tenir compte, par exemple, du volume? Si le volume est relativement petit, la batch pourrait avoir un effort constant, puis dire : « Ok, je vais vérifier les 7 derniers jours, supposons. » Donc on lui donnerait, sans que ce soit compliqué, un budget de temps ou d'effort en nombre de records, par exemple. À budget constant, si le volume est très élevé d'activité, la batch pourrait décider de vérifier l'intégrité seulement sur deux journées la nuit. Si le volume est petit, la batch pourrait décider de vérifier systématiquement les 14 dernières journées, à l'autre extrême. Je verrais quelque chose qui permettrait de moduler l'effort et de tirer le maximum des concepts de sécurité qu'on a en place, avec un mécanisme bref qui permet de gérer l'effort.
>
> Ce qui est important dans tout ça, c'est de rendre clair sur le dashboard ce qu'on fait en termes d'analyse de sécurité. Et ça, c'est un autre aspect que je vais discuter à part. [→ voir D6]

## D7 — Email integration: product vision and deployment profiles

> Verbatim (FR):
>
> On va introduire la notion de courriel avec l'API Java de courriel. Donc, présentement, dans Ezkey, on a des placeholders avec des disclaimers qui viennent indiquer qu'on affiche, par exemple, un code QR et que, dans la vraie vie, ce serait un canal séparé, typiquement courriel.
>
> Donc, pour certains types d'intégration, par exemple pour les SMS, on va créer des projets périphériques qui ne seront pas dans le noyau de la plateforme d'Ezkey, c'est-à-dire qu'on va créer, par exemple, `ezkey-sms-twilio`. Par contre, pour les courriels, c'est un cas particulier, parce qu'il y a des API Java pour le prendre en charge, ce qui fait que on reste dans le domaine de l'intégrité de la plateforme sans créer de dépendance à l'extérieur, ce qui n'est que de la configuration.
>
> Donc, ça prend un plan d'introduction des courriels dans Ezkey, et là, la première tâche, ça va être de clarifier la vision qu'on a. Il faut prévoir qu'on va faire des envois de courriel pour inviter quelqu'un qui est en train de faire son enrôlement pour lui communiquer son code QR. Ça, c'est un cas. On a aussi sûrement le cas particulier d'un administrateur que l'on crée avec code d'activation. Certainement qu'on va vouloir lui envoyer un courriel avec son code d'activation, ce serait à confirmer. Donc, est-ce qu'on a d'autres situations où on veut un courriel?
>
> Ici, le point, c'est que cette partie de ce que je te dis là, ce n'est pas de faire le plan jusqu'à l'implémentation, mais plutôt de faire un positionnement produit avec un brainstorming, un grillage. Il va falloir vraiment voir comment on va introduire, par phase, l'utilisation du courriel, puis maximiser le bon usage de ce que l'on veut comme stratégie d'utilisation du courriel dans les équipes ou la gestion de la sécurité, une bonne communication. Est-ce qu'il y a des features, des méthodes de workflow dans Ezkey qu'on va rendre optionnel ou paramétrable au niveau courriel? Ça reste à voir aussi et aussi trouver c'est quoi la stratégie de cohabitation avec le mode actuel, parce que je vois quand même peut-être une certaine valeur pragmatique au mode tout en un qu'on a présentement.

Ce n'est peut-être pas celui qu'on valorise le plus, ou, à tout le moins, on veut le baliser, expliquer les implications et éduquer notre auditoire sur les conséquences de ce choix.
