## Context (observed in code)

- `ezkey_audit_log.audit_log_id` is `BIGINT GENERATED ALWAYS AS IDENTITY`
  (`V4__partitioning_auth_audit_and_function.sql`). PostgreSQL backs it with an implicit sequence in
  schema `public`.
- The table is composite-partitioned: RANGE (`created_at`) by month, then LIST (`api_name`) with
  `_admin` / `_auth` / `_integration` sub-partitions. Identity/sequence lives on the parent.
- `AuditLog` entity uses `@GeneratedValue(strategy = GenerationType.IDENTITY)`.
- `AuditLogService.log()` seals each row in a single `PROPAGATION_REQUIRES_NEW` transaction with a
  **two-step write**:
  1. `save()` → INSERT, DB assigns `audit_log_id`;
  2. `entityManager.refresh(saved)` → re-read `created_at` at PostgreSQL microsecond precision;
  3. `computeHmac(saved)` → canonical form, field 1 = `audit_log_id`, field 13 = `created_at`;
  4. `save()` → UPDATE `entry_hmac`.
- `AuditHmacService.formatTimestamp` already truncates to `MICROS`; the refresh exists because Java
  `now()` nanoseconds vs PostgreSQL microsecond rounding previously failed ~50% of verifications.
- **Single-writer confirmed:** the only INSERT/UPDATE into `ezkey_audit_log` is
  `AuditLogService.log()` (`auditLogRepository.save` at two call sites). All other repository usage
  is read (`findAll`, `count`, `existsByCreatedAtBefore`) or the admin-only purge
  (`deleteOlderThan`). No other code path writes audit rows, so converting this one path fully
  removes the peripheral UPDATE need.
- `apply-grants.sql` already grants `USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public` to the three
  runtime roles; peripherals currently hold `SELECT, INSERT, UPDATE` on `ezkey_audit_log`.

## Critical questions and analysis

### Q1 — Named sequence vs implicit identity sequence for JPA `@SequenceGenerator`?
`GENERATED BY DEFAULT AS IDENTITY` still creates an *implicit* sequence with an auto-generated name.
JPA `GenerationType.SEQUENCE` needs a `sequenceName`. Two options:

- **(a, recommended)** Define an **explicit named sequence** in the Flyway baseline (owned by
  `ezkey_migrate`), set the column default to draw from it, and point `@SequenceGenerator` at that
  name. Explicit ownership, stable name, clean grant story.
- **(b)** Point `@SequenceGenerator` at the implicit identity sequence name. Fragile: couples Java
  to a PostgreSQL-generated name and to the column's ownership of the sequence.

**Recommendation:** (a) explicit named sequence.

### Q2 — `allocationSize` on the JPA sequence generator?
Hibernate's default pooled optimizer (`allocationSize = 50`) reserves ranges and reduces `nextval`
calls but produces larger, less intuitive id gaps.

- **(recommended)** `allocationSize = 1`: monotonic, simplest to reason about; one `nextval` per
  audit row (cheap; identity already does one per insert). Gaps on rollback still possible and
  acceptable.
- Pooled: marginal write-throughput gain, larger gaps. Not worth the reasoning cost for audit.

**Recommendation:** `allocationSize = 1`.

### Q3 — What guards against a silent `created_at` mismatch?
This is the crux. If app-owned `created_at` ever differs from the stored value, HMAC verification
fails silently. **Characterization test (mandatory before removing the refresh):** persist an audit
row through the new path, read it back from the DB, and assert `verifyHmac` passes — including
sub-microsecond `now()` inputs, month/partition boundaries, and a non-UTC JVM default timezone.

### Q4 — Does removing the second write regress the integrity subsystem?
Nightly/retroactive validation, chain checkpoints, entry conciliation, and `verifyHmac` read
`entry_hmac` and the canonical fields — all unchanged by this refactor. Risk is low but must be
covered by the existing integrity suite (regression run, not new design).

### Q5 — HA / clock ownership of `created_at`?
Today `created_at` uses the DB `DEFAULT CURRENT_TIMESTAMP` (DB clock); the new path uses the app
clock. On a single node this is identical; across HA nodes the app/DB clocks may differ by a few ms
— irrelevant except at a month-boundary microsecond, where it only decides the partition, not
correctness. Acceptable; note it. (Alternative if ever needed: `INSERT ... RETURNING created_at` —
but that reintroduces a read and is unnecessary if the app owns the value.)

## Open questions (resolved 2026-07-18)

- **OQ1 → G8:** Explicit named sequence in the Flyway baseline.
- **OQ2 → G9:** `allocationSize = 1`.
- **OQ3 → G10:** Application owns `created_at`; no `RETURNING` fallback needed.

## Risks and exception paths

- **Silent verification regression** (created_at mismatch) → mitigated by G6 + Q3 characterization
  test. Highest-signal risk.
- **Sequence/grant edge cases** on the partitioned parent → `verify-grants.sh` positive (peripheral
  INSERT works) + negative (peripheral UPDATE denied) assertions.
- **`GENERATED ALWAYS` → `BY DEFAULT` migration scope creep** → keep migration to the identity
  definition only; do not restructure the table or partitions.
- **Over-engineering guardrail** (from `TB-2026-07-16`): if validation shows the single-INSERT path
  compromises atomicity or forces a detection-gap window, keep the current atomic two-step seal as
  the pragmatic baseline rather than pursuing INSERT-only as dogma.

## Rejected alternatives (brief)

| Alternative | Why rejected |
|-------------|--------------|
| DB trigger computes/writes the HMAC seal | Moves cryptographic responsibility (and key material) into PostgreSQL — undesirable a priori. |
| Admin-api batch/event seals peripheral rows | Introduces a window where a manipulation currently detected would not be; extra moving parts. |
| Keep INSERT + UPDATE, just grant it | Status quo; leaves the "peripherals never mutate audit rows" story unfulfilled at the DB boundary. |
| `OVERRIDING SYSTEM VALUE` on `GENERATED ALWAYS` | Works, but `GENERATED BY DEFAULT` is the idiomatic JPA-friendly form and keeps inserts clean. |
