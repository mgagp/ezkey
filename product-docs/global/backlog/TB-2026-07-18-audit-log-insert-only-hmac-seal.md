## Objective

Replace the two-step HMAC seal in `AuditLogService.log()` (INSERT to obtain `audit_log_id`, then
UPDATE `entry_hmac`) with a **single INSERT** that already carries a pre-allocated `audit_log_id`,
an application-owned `created_at`, and the computed `entry_hmac` — all inside the existing
`REQUIRES_NEW` transaction. Then tighten `ezkey_auth` and `ezkey_integration` to **SELECT + INSERT**
on `ezkey_audit_log` (drop UPDATE), restoring the least-privilege intent of the role split without
losing atomicity or changing the HMAC canonical form.

## Boundaries in scope

- `ezkey-core` migration: `audit_log_id` → `GENERATED BY DEFAULT AS IDENTITY` backed by an explicit
  **named sequence** owned by `ezkey_migrate` (folded into the Flyway baseline; greenfield).
- `AuditLog` entity: `@GeneratedValue(strategy = SEQUENCE)` + `@SequenceGenerator` (allocationSize 1).
- `AuditLogService.log()`: allocate id → set `created_at` (micros-truncated) → compute HMAC →
  single INSERT; remove `entityManager.refresh` and the second `save`.
- `scripts/db/apply-grants.sql`: peripheral roles → `SELECT, INSERT` on `ezkey_audit_log`
  (drop UPDATE); `ezkey_admin` unchanged (keeps INSERT/UPDATE/DELETE).
- `scripts/db/verify-grants.sh`: negative assertion that peripheral **UPDATE on `ezkey_audit_log`
  is denied**; positive assertion that INSERT still works.
- `docs/DATABASE_ROLE_PERMISSIONS_MATRIX.md`: update the `ezkey_audit_log` row + Explicit
  exceptions #1 to reflect peripheral INSERT-only.
- Characterization test in `ezkey-core` for the sign → persist → read-back → `verifyHmac` round trip.

## Out of scope

- Changing the HMAC algorithm, key handling, or `buildCanonicalForm` field order/semantics.
- DB-side HMAC (trigger/PL) or admin-batch sealing.
- Applying the same identity redesign to `ezkey_auth_attempt` or other IDENTITY tables (pattern is
  reusable but not part of this slice).
- Row-level security / column-level grants.
- `ezkey_keyset_blob` Admin-first bootstrap and alert retention/purge (separate ideas).
- **Audit write fail-open / exception swallow in `AuditLogService.log()`** — delivery guarantee and
  honesty messaging live in
  [`ideas/I-2026-07-18-audit-log-fail-open-exception-swallow.md`](ideas/I-2026-07-18-audit-log-fail-open-exception-swallow.md)
  (`captured`, `P2`). This TB does not change fail-open behaviour.

## First executable slice

Convert the single audit write path end to end on the clean-start stack: an audit event from each
API is persisted with one INSERT (id + `created_at` + `entry_hmac` set), `verifyHmac` passes, and
`ezkey_auth` / `ezkey_integration` can no longer UPDATE `ezkey_audit_log`.

## Rollback or fallback posture

- If the characterization test shows any `created_at` sign/stored mismatch that micros-truncation
  cannot close, fall back to `INSERT ... RETURNING created_at` (single statement, one read) before
  computing the HMAC — still a single mutating statement, still no UPDATE grant.
- If single-INSERT sealing cannot preserve atomicity or introduces a detection-gap window, revert to
  the current atomic two-step seal and keep the peripheral UPDATE grant (documented status quo from
  `TB-2026-07-16`). INSERT-only is the goal, not dogma.

## Critical flows

- **Nominal:** build `AuditLog` → allocate id via named sequence → set micros-truncated
  `created_at` → compute HMAC → single INSERT → row present and sealed atomically.
- **Rollback:** exception before commit → whole `REQUIRES_NEW` transaction rolls back; sequence gap
  is acceptable; no partial/unsealed row.
- **Grant boundary:** `ezkey_auth` / `ezkey_integration` INSERT succeeds; their UPDATE on
  `ezkey_audit_log` is denied by PostgreSQL.
- **Integrity chain:** nightly/retroactive validation, chain checkpoints, entry conciliation still
  read `entry_hmac` + canonical fields unchanged.

## Test posture (resolved 2026-07-18)

Testing posture explicitly settled during design (see idea § Test posture). Rationale: the HMAC
canonical form is unchanged, so existing crypto unit tests stay valid; the only new risks are
(a) the write-path refactor invariant and (b) the grant boundary. **Critical nuance:**
`AuditLogService.log()` swallows exceptions silently — a seal/grant regression does **not** fail an
API call, it only appears as missing or unsigned audit rows. The functional integrity elective is
therefore the load-bearing safety net for this slice.

- **Real-DB round trip:** rely on the existing functional elective `AuditIntegrityElectiveTest`
  (Docker, real PostgreSQL) — no Testcontainers added to `ezkey-core` (stay within the stack). It
  recomputes every persisted signed row's HMAC via `/audit-logs/integrity-check`; any `created_at`
  sign/stored mismatch would surface as `invalidEntries > 0`.
- **Elevated gate:** for this slice, the functional suite + `AuditIntegrityElectiveTest` on a
  clean-start stack **under tightened grants** is a **required** closeout gate (not on-demand only),
  precisely because `log()` fails silently.
- **New write-path unit test** (Mockito, style of `AuditLogServiceRetentionGuardTest`): `log()` calls
  `save()` exactly once, never calls `entityManager.refresh(...)`, and sets the id + micros-truncated
  `created_at` before computing the HMAC.

## Evidence plan

- **Unit (existing, unchanged):** `AuditHmacServiceTest` — canonical form, compute/verify, tamper,
  and the sub-microsecond truncation / rounding cases stay green (canonical form untouched).
- **Unit (new):** write-path invariant test (single `save`, no `refresh`, id/`created_at` before
  HMAC).
- **Integrity regression:** existing nightly/retroactive/chain/conciliation suites pass unchanged.
- **Functional (required gate):** clean-start stack under segregated roles; standard functional
  suite + `AuditIntegrityElectiveTest` green (rows from all three APIs present, signed, and verify);
  `verify-grants.sh --docker` passes with the new peripheral INSERT-only assertions (UPDATE denied,
  INSERT allowed).
- **Docs/traceability:** matrix row + Explicit exceptions #1 updated; `I-2026-07-18` → `done`;
  `TB-2026-07-16` follow-up marked resolved; grill session linked.

## Quality gates

- **Analysis gate:** grill complete (G1–G10 settled) + test posture settled — met.
- **Design gate:** migration shape (named sequence + `GENERATED BY DEFAULT`), JPA mapping, and
  `created_at` ownership contract confirmed before coding.
- **Implementation gate:** `./scripts/build.sh` baseline green (incl. new write-path unit test);
  integrity regression + `verify-grants.sh` negative assertion + `AuditIntegrityElectiveTest` on a
  clean-start stack under tightened grants all pass (required gate — see Test posture).

## Exit criteria

An audit event from each API is written with a single INSERT and verifies; `ezkey_auth` and
`ezkey_integration` hold only SELECT + INSERT on `ezkey_audit_log` (UPDATE denied, DELETE denied);
atomicity and the HMAC canonical form are unchanged; matrix, grants, verifier, and traceability all
reflect peripheral INSERT-only.
