# Enrollment Admin UI Review

## Scope

Prioritize the enrollment detail page first, then the metadata edit flow, then the paginated enrollment list.

Backend intervention is explicitly in scope when required to align the Admin UI with the enrollment data model, response payloads, and update contract.

## Current Findings

- The persisted enrollment model contains more operational fields than the Admin UI currently surfaces, notably `createdAt`, `createdByAdminId`, `deactivatedAt`, `deactivatedByAdminId`, `revokedAt`, and `revokedByAdminId` in `[C:/github/ezkey/ezkey-core/src/main/java/org/ezkey/enrollment/domain/entity/Enrollment.java](C:/github/ezkey/ezkey-core/src/main/java/org/ezkey/enrollment/domain/entity/Enrollment.java)`.
- The current admin response DTO does not expose some of those attributes at all, so the detail-page review is partly a UI task and partly an API/DTO completeness task in `[C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/enrollment/dto/EnrollmentResponseDto.java](C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/enrollment/dto/EnrollmentResponseDto.java)`.
- The detail page currently shows only a subset of available fields and keeps the edit dialog limited to metadata fields in `[C:/github/ezkey/ezkey-admin-ui/src/pages/enrollment-detail.tsx](C:/github/ezkey/ezkey-admin-ui/src/pages/enrollment-detail.tsx)`.
- The list page currently shows `id`, `name`, `status`, `active`, `integration`, `challenge`, and `verifiedAt`, and its status filter still omits `REVOKED` and `EXPIRED` in `[C:/github/ezkey/ezkey-admin-ui/src/pages/enrollments.tsx](C:/github/ezkey/ezkey-admin-ui/src/pages/enrollments.tsx)`.
- The metadata PATCH is intentionally narrow and only applies to active `VERIFIED` enrollments, which aligns with the idea that many enrollment attributes are workflow-bound rather than freely editable; however, null-clearing semantics are weak today for `contactEmail` and `expiresAt` in `[C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/admin/service/EnrollmentUpdateService.java](C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/admin/service/EnrollmentUpdateService.java)` and `[C:/github/ezkey/ezkey-admin-ui/src/pages/enrollment-detail.tsx](C:/github/ezkey/ezkey-admin-ui/src/pages/enrollment-detail.tsx)`.
- The plan now assumes that backend contract changes are acceptable where needed, including DTO enrichment, PATCH semantics, validation rules, and any narrow extension of editable metadata required to support the approved UI behavior.
- A dedicated reset workflow exists for administrator MFA enrollments only, via recovery, in `[C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/admin/controller/AdminEnrollmentController.java](C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/admin/controller/AdminEnrollmentController.java)`. No equivalent general rebind/reset workflow was identified for ordinary user enrollments.

## Plan

1. Build an enrollment attribute matrix from backend to UI.
  - Classify each maintained attribute as: `show on detail`, `keep hidden`, `editable metadata`, or `workflow-specific / separate plan`.
  - Use the entity and admin DTO/controller as the source of truth, and explicitly note where the current backend contract must change to support the target UI:
    - `[C:/github/ezkey/ezkey-core/src/main/java/org/ezkey/enrollment/domain/entity/Enrollment.java](C:/github/ezkey/ezkey-core/src/main/java/org/ezkey/enrollment/domain/entity/Enrollment.java)`
    - `[C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/enrollment/dto/EnrollmentResponseDto.java](C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/enrollment/dto/EnrollmentResponseDto.java)`
    - `[C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/admin/dto/request/EnrollmentUpdateRequestDto.java](C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/admin/dto/request/EnrollmentUpdateRequestDto.java)`
2. Revise the detail page to expose the right operational fields.
  - Expand `[C:/github/ezkey/ezkey-admin-ui/src/pages/enrollment-detail.tsx](C:/github/ezkey/ezkey-admin-ui/src/pages/enrollment-detail.tsx)` so operators can see the most relevant enrollment facts without overexposing cryptographic internals.
  - Candidate additions for the detail view:
    - `createdAt`
    - `createdByAdminId`
    - `deactivatedAt` and `deactivatedByAdminId` when applicable
    - `revokedAt` and `revokedByAdminId` when applicable
    - `version` only if useful for operator/debug visibility
  - Keep workflow-bound fields under review rather than blindly exposing them as editable: `status`, `active`, proof token, challenge, device binding material, and any field whose change would imply rebind/reset semantics.
3. Close API/DTO gaps required by the detail review.
  - If the approved detail design needs fields not currently returned, extend the admin enrollment response DTO and mapper in:
    - `[C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/enrollment/dto/EnrollmentResponseDto.java](C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/enrollment/dto/EnrollmentResponseDto.java)`
    - `[C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/enrollment/mapper/EnrollmentAdminMapper.java](C:/github/ezkey/ezkey-admin-api/src/main/java/org/ezkey/enrollment/mapper/EnrollmentAdminMapper.java)`
  - Ensure the PATCH response remains coherent with GET-by-id when the UI refreshes detail state.
  - Adjust backend contract semantics where necessary, not just response shape, for example null-clearing behavior, validation rules, or a deliberately expanded editable field set if the review justifies it.
4. Reassess the metadata edit surface against real workflows.
  - Validate that the current editable set remains the right one: `enrollmentName`, `contactEmail`, `userIdentifier`, `authAttemptChallengeRequired`, `expiresAt`.
  - Accept backend/API changes as part of the solution if the current PATCH contract is too restrictive or semantically misleading for the desired UI behavior.
  - Explicitly identify non-editable fields that should stay process-driven instead of form-driven, and capture missing workflows separately.
  - Review whether clear/remove semantics should be supported for optional fields such as `contactEmail` and `expiresAt` instead of only overwrite semantics.
5. Reassess the paginated list columns and ordering.
  - Review the current list in `[C:/github/ezkey/ezkey-admin-ui/src/pages/enrollments.tsx](C:/github/ezkey/ezkey-admin-ui/src/pages/enrollments.tsx)` for operator usefulness and scanability.
  - Confirm whether the current compact set is still optimal or whether one additional column would materially help, likely from `userIdentifier`, `contactEmail`, `lastUsedAt`, or `createdAt`.
  - Revisit column order to match operator workflow, and align filters with actual backend statuses by including `REVOKED` and `EXPIRED` if the screen is meant to support full lifecycle monitoring.
6. Produce explicit recommendations and out-of-scope follow-ups.
  - Deliver a short recommendation set for:
    - fields to add to detail now
    - fields to keep editable now
    - list-column changes to make now, if any
    - workflow gaps to handle in a separate plan, especially for rebind/reset-style changes outside admin recovery

## Expected Output

- A more complete enrollment detail view for operators.
- A validated and intentionally limited metadata edit surface, backed by an explicit and aligned backend contract.
- A confirmed or adjusted enrollment list column set and ordering.
- A separate backlog note for workflow-specific enrollment changes that should not be solved by generic metadata editing.
